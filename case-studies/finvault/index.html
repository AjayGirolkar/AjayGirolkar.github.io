01 — THE PROBLEMA résumé can't prove you've shipped regulated software.

Fintech founders and neobank CTOs hire iOS engineers on one question they can't answer from a CV: has this person built software where a security review, not a designer, is the gate?

The usual portfolio answer is a beautiful dashboard over hardcoded JSON. It proves taste. It proves nothing about Keychain access-control flags, attestation, certificate pinning, or what happens when a transfer fails halfway. So the brief I set myself was narrow and testable:

Build the thing a reviewer can audit — where every claim in the README opens a file that actually runs.

That constraint drove every decision below, including the ones that cost time and the ones I chose to leave unfinished.

02 — ARCHITECTUREProtocols at every seam, so the backend could change underneath.

FinVault is MVVM + Coordinator over clean layering. Views bind to @Observable @MainActor view models; coordinators own navigation and dependency construction, so no view ever builds its own service. Every cross-layer boundary — View → ViewModel → Use Case → Repository — is a protocol.

That sounds like architecture-for-its-own-sake until the migration. The app shipped its first version reading bundled JSON fixtures. It now runs on live Supabase Postgres with row-level security, real GoTrue auth, and server-side Edge Functions for anything that moves money. Fifteen repositories swapped implementation. Not one view model changed.

The same seam is why the test suite is fast and deterministic: use cases and view models run against in-memory stubs with no network at all.

Errors are typed, end to end

One VaultError model spans the app. No stringly-typed failures, no silent try?. Each layer maps foreign errors — SecurityKit, GoTrue, Postgres — into the domain model at its own boundary, which is the only place that knows enough to do it right.

03 — SECURITYThe claims, and exactly how far each one is wired.

This is the table reviewers actually read, so it states the truth including the parts that aren't finished. "Live" means it runs in the app today. "Wired, not activated" means the code path exists and compiles but is deliberately switched off pending one production step — named in each row.

Why pinning ships switched off

Attaching a pinning delegate with an empty hash set rejects every TLS challenge — a total outage, shipped as a security feature. Default-off is the safe state, and the activation step is a real trap worth writing down: the validator hashes the raw key bytes from SecKeyCopyExternalRepresentation, not the DER SubjectPublicKeyInfo. The openssl one-liner everyone pastes from a blog post produces a hash that can never match. The value has to be captured on-device against the live chain.

Getting that wrong silently is exactly the class of bug this whole project exists to demonstrate I know how to avoid.

04 — DESIGN SYSTEMOne accent, and a rule the codebase enforces.

Seventeen feature modules is enough surface for a design language to drift into seventeen dialects. So the visual layer is a token system — FinColors, FinTypography, FinSpacing / FinRadius — with a component set on top: FinCard, FinAmountText, FinDeltaPill, FinEmptyState.

The governing rule is a single line: no raw colors or fonts inside Features/. One accent. Gain and loss appear only on numbers, deltas and status dots — never as fills, because a green card is a mood and a green number is information. Motion is gated on Reduce Motion.

The rule is enforced as a review gate and encoded as a reusable agent skill, so it survives the twelfth feature rather than only the first two.

05 — METHODSenior engineer as architect, AI agent as the typing.

FinVault was built in tightly-scoped agent sessions: a written hand-off TODO at the end of each one so context survives, project conventions captured as reusable skills so they're never re-derived, and a token budget tracked per task. Architecture decisions, security judgement and the ship/don't-ship calls stayed human. The boilerplate did not.

The measurable result is scope: 31.7k lines, a full backend migration, and a documented ship checklist, at side-hustle hours. The honest result is that the workflow amplifies whoever is driving it — the pinning trap above wasn't caught by the agent, it was caught by knowing where to look.

06 — OPEN WORKWhat isn't done, and what each item is blocked on.

A case study that ends at "and everything shipped perfectly" isn't a case study. Here's the current ship checklist, with the actual blocker on each line.

  • Pinning activation — needs a one-time on-device SPKI hash capture against the live chain (leaf + intermediate, for rotation safety).
  • App Attest enforcement — needs an entitlements file wired through CODE_SIGN_ENTITLEMENTS; synchronized folders don't wire it for you.
  • First-run experience — seeded personas have data; a real signup lands on empty tables. Blocked on a product call: manual entry vs. statement import. Statement import is half-built and wins.
  • Observability — structured os_log + MetricKit + a user-facing audit-log screen, since audit_events already populates. No third-party SDK.
  • Push — deliberately blocked. FCM means adding Firebase to a zero-dependency app target; the server-side APNs HTTP/2 path keeps the client clean. Decision pending, not oversight.

Each of those is a paragraph in the repo's ship checklist with the trap written down, which is the point: the interesting engineering artifact isn't the finished app, it's the record of what the finishing actually costs.

Deliberately out of scopeAccount aggregator integration · real KYC · anything requiring a licence
Ship pathTestFlight with real signups — pure engineering, no vendor or regulatory work

07 — OUTCOMEWhat this repo demonstrates.

A flagship transfer flow that feels shipped: App Attest gate → biometric unlock → source and destination → amount and memo → review with biometric re-auth and a 6-digit OTP → server-side posting → balances and audit log update, with a haptic on success. Empty, loading and error states on every screen on that path. Dynamic Type, VoiceOver, light and dark.

Behind it: a security layer that's auditable rather than asserted, a layering that survived a complete backend swap without view-model churn, and a written account of the parts still switched off and why.

The claim was never "this is a bank." It's that the seams are in the right places, and you can check.
